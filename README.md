# Сервис прогнозирования медианной зарплаты в банковской сфере

## 1. Бизнес-анализ (Business Understanding)

### Цели и границы проекта
Главная цель проекта — создать модель машинного обучения, которая сможет точно прогнозировать медианную заработную плату кандидатов в банковском секторе. Прогноз строится на основе набора компетенций, профессиональных навыков и социальных показателей соискателей.

*   **Организационная структура:** 
    *   *Заказчик сервиса:* Банковские HR-департаменты, руководители отделов подбора персонала, специалисты по компенсациям и льготам (C&B).
    *   *Основной пользователь:* HR-специалисты, рекрутеры, линейные руководители.
*   **Бизнес-цель:** Оптимизация затрат на ФОТ, ускорение процесса найма, формирование конкурентных и справедливых зарплатных предложений для кандидатов, уменьшение оттока специалистов из компании к конкурентам.
*   **Текущие решения:** Оценка рынка чаще всего проводится вручную через стандартные отчеты или базовую аналитику. Текущий подход не устраивает долгой скоростью обработки данных и низкой точностью при учете редких комбинаций навыков, что влечет за собой риски переплаты или потери ценных кадров.

#### Риски проекта и план действий по их уменьшению
1.  **Риск:** Не уложиться в сроки разработки сервиса.
    *   *Решение:* Итеративное планирование. Использование готовых стабильных библиотек для парсинга, NLP и моделирования. Быстрое развертывание базовой модели (Linear Regression baseline) для непрерывного контроля прогресса.
2.  **Риск:** Малое количество, высокий дисбаланс или плохое качество данных с HeadHunter (пропущенные значения, МРОТ-шум).
    *   *Решение:* Проведение многоэтапной очистки данных (EDA). Выжигание небанковского мусора по регулярным выражениям, фильтрация МРОТ-шума (отсечение окладов ниже 27 000 руб.). Жесткая очистка выборки от дефицитных, высокодисперсных классов (ИТ, HR) и фокусировка на стабильных b2b-сегментах банковского ритейла с объемом данных $N \ge 30$ на класс.
3.  **Риск:** Данные качественные, но прямая математическая закономерность между текстовыми навыками и зарплатой в рублях слабая или аномальная.
    *   *Решение:* Применение гибридного NLP-анализа. Извлечение скрытых семантических контекстов из названий вакансий с помощью предобученной нейросети `RuBERT-tiny` с последующим сжатием эмбеддингов через PCA до главных компонент. Привлечение HR-экспертов для ручной настройки иерархического переброса вложенных должностей (выделение VIP-сегментов, Комплаенса, Резерва и фиксация грейдов).

### 1.2 Решаемые задачи с точки зрения аналитики (Data Mining goals)

Постановка задачи переведена в технические термины машинного обучения. Мы решаем задачу **восстановления регрессии** (прогнозирование непрерывной величины — рыночной заработной платы в рублях).

*   **Метрики качества:**
    *   **MAE (Mean Absolute Error):** Средняя абсолютная ошибка в рублях. Выбрана в качестве основной функции потерь при обучении градиентного бустинга (`objective="reg:absoluteerror"`), так как математически настраивает модель на предсказание устойчивой к выбросам **медианы** распределения окладов.
    *   **MAPE (Mean Absolute Percentage Error):** Показывает среднюю относительную ошибку в процентах. Является главной бизнес-метрикой, так как легко интерпретируется конечными пользователями (HR-департаментом).
*   **Критерий успешности модели:**
    *   *Минимальный порог:* MAPE ≤ 25% на кросс-валидации по всем классам.
    *   *Достигнутый результат:* Итоговый MAPE усложненного XGBoost зафиксирован на уровне **21.7%** (при MAE ~32 673 руб.), что полностью удовлетворяет бизнес-требованиям заказчика. Базовая модель (Linear Regression) показала неприемлемую ошибку в 35.3%.

### 1.3 План проекта (Project Plan)

План включает в себя последовательное прохождение всех шести фаз методологии CRISP-DM:
1.  **Бизнес-анализ:** Определение b2b-целей, техническая постановка задачи, оценка рисков и фиксация метрик успешности.
2.  **Анализ данных (Data Understanding):** Сбор кэша HTML-страниц с HeadHunter, семантическая разметка матрицы признаков $X$, исследование распределений окладов.
3.  **Подготовка данных (Data Preparation):** Извлечение текстовых триггеров навыков, генерация RuBERT-эмбеддингов, иерархическая группировка должностей, строгая типизация категориальных признаков.
4.  **Моделирование (Modeling):** Запуск байесовской оптимизации гиперпараметров в `Optuna` (15 итераций) с валидацией через `StratifiedKFold` строго по классам рынка. Обучение финальной продакшн-модели.
5.  **Оценка решения (Evaluation):** Проверка моделей на Out-of-Fold предсказаниях, формирование детального поклассового текстового отчета по метрикам MAE/MAPE, валидация бизнес-логики.
6.  **Внедрение (Deployment):** Сериализация весов финальной модели в легковесный JSON-формат, интеграция в API, настройка CI/CD автоматизации.

## 2. Архитектура Системы и Стек технологий

*   **Язык разработки:** Python 3.10 / 3.14
*   **Фреймворк машинного обучения:** XGBoost (Regressor)
*   **Оптимизация гиперпараметров:** Optuna (Байесовский сэмплер TPE)
*   **NLP-движок:** Трансформер `cointegrated/rubert-tiny` (Извлечение семантики названий вакансий)
*   **Размерность векторов:** Сжатие эмбеддингов RuBERT через PCA до 3–8 главных компонент
*   **Инференс и API:** FastAPI (Веб-сервер), Celery (Асинхронный воркер задач), Redis (Брокер очередей)
*   **База данных:** СУБД PostgreSQL (Хранение истории предсказаний и логов обратной связи от HR)

### Поддерживаемые целевые роли (Банковский ритейл, N >= 30):
*   Представители банка / Доставка карт
*   Прямые продажи / DSA
*   Операционисты / Сервис-менеджеры
*   Кассиры
*   Менеджеры и главные менеджеры по продажам розничного блока
*   Персональные менеджеры VIP / Private
*   Менеджеры и руководители блоков обслуживания Юридических Лиц (ЮЛ)
*   Руководители Дополнительных Офисов (ДО)

## 3. Инструкция по запуску через Docker Compose (How to Run)

Весь b2b-сервис полностью контейнеризирован. Вы можете развернуть всю инфраструктуру (БД, брокер, бэкенд, многопоточный воркер и UI) одной командой.

### Шаг 3.1: Сборка и запуск контейнеров
Убедитесь, что у вас запущен Docker Desktop, и выполните в корне проекта:
```bash
docker compose up --build
```

**Компоненты развернутой сети (`salary_network`):**
1.  `salary_postgres_db` (PostgreSQL 15): Хранилище сессий на порту `5432`.
2.  `salary_redis_broker` (Redis 7): Брокер сообщений на порту `6379`.
3.  `salary_fastapi_backend` (FastAPI): Веб-сервер на порту `8000`. Запущен с флагом `--reload` для автоматического подтягивания изменений кода без пересборки.
4.  `salary_celery_worker` (Celery): Распределенный воркер. Настроен prefork-пул (`--concurrency=4`), позволяющий параллельно обрабатывать до 4 резюме соискателей, задействуя ядра процессора для расчетов RuBERT и SHAP.
5.  `salary_streamlit_ui` (Streamlit): Веб-интерфейс для HR-специалистов на порту `8501`.

*Для остановки сервиса используйте команду: `docker compose down -v`.*

## 4. Качество кода и Локальное тестирование

Если вы вносите изменения в код локально и хотите прогнать тесты/линтеры вне Docker, выполните следующие команды в вашей системе:

### Шаг 4.1: Установка инструментов контроля качества
```bash
pip install pytest pytest-mock black flake8 psycopg2-binary shap
```

### Шаг 4.2: Проверка форматирования (Black)
```powershell
python -m black . --line-length 120
```

### Шаг 4.3: Статический анализ (Flake8)
Линтер автоматически скроет предупреждения о длинных строках регулярных выражений из словарей согласно правилам корневого файла `.flake8`:
```powershell
python -m flake8 . --ignore=W503,E203,E501,E402,E722,F541
```

### Шаг 4.4: Запуск 6 основных ML-тестов (Pytest)
Тестирование бэкенда полностью изолировано от Docker-контейнера СУБД. `pytest` автоматически разворачивает изолированную базу PostgreSQL в оперативной памяти через SQLite (`StaticPool` в `tests/conftest.py`), а тяжелые модели и SHAP мокаются умными динамическими заглушками:
```powershell
python -m pytest tests/ --verbose
```

## 5. Конвейер Непрерывной Интеграции (CI/CD)

В проекте настроен автоматический CI-пайплайн на базе **GitHub Actions** (`.github/workflows/ci-main.yml`). 

При каждом слиянии (мердже) Pull Request или пуше в ветку `main` облачный сервер автоматически разворачивает среду, проверяет стиль кодовой базы утилитой `black` и прогоняет статический анализ `flake8`. После этого запускаются 6 core ML-тестов. Если линтер находит ошибки или падает хотя бы один тест, пайплайн блокирует слияние, гарантируя стабильность продакшн-окружения.
